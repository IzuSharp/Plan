## 项目边界

NativeWeave独立于ArcForges，ArcForges只参考格式。C#是应用开发层，正式消费必须Native AOT。Database底层必须Rust，managed驱动只作源码/基准对照；Rust Server可选且需证据。优先源码驱动深度复用；普通新实体使用预编译native能力，不默认Cargo/CI。自然typed Fluent优先，不要求完整IQueryable/EF，不在C#重写SQL AST/方言。SG可选生成static metadata/DTO，不是唯一查询路径。Core只提供可组合ABI/lifetime/buffer/error/async，无巨型runtime。保留严格安全和生产验收，不授权大规模产品实现。

## 具体编制责任

原生Server成熟接缝和body预算，Kestrel对照/可选协议保持局部依赖。

Research输入：R26, R27, R28, R29, R30。

### R26 — Kestrel与纯C# AOT服务器基线
- Kestrel现代Native AOT能力等价基线；保留独立无DB示例，源码可绑定不等于Server有实测收益。
- 现有C# stack能完成哪些目标；handler如何静态生成；HTTP生命周期/内存池/connection limit怎样控制
固定来源见实际R evidence；引用不等于已读。

### R27 — Rust网络引擎与C# Handler边界
- Hyper Service/Body、Tower/Axum、Actix worker affinity、Pingora代理接缝；C#是handler层，不重写网络核心。
- 把网络搬到Rust究竟减少还是增加分配/调度；HTTP模型怎样跨ABI；是否能避免重复TLS和两套executor
固定来源见实际R evidence；引用不等于已读。

### R28 — gRPC、MCP、TLS与协议适配
- 所选gRPC/MCP/TLS的静态注册/DTO与错误；协议包选择不阻塞无关Server/DB工作。
- 协议与transport怎样分层；gRPC代码生成和MCP序列化可否AOT；TLS证书与认证归谁；协议版本如何固定
固定来源见实际R evidence；引用不等于已读。

### R29 — 请求流、背压、超时与优雅关闭
- Tower ResponseFuture许可不覆盖body；Hyper H2credit不覆盖retained bytes；waiters/chunks/close预算分别验证。
- 请求与响应双向背压怎样贯通FFI；容量预算由字节还是条目限制；关闭时新请求/已接受请求如何处理
固定来源见实际R evidence；引用不等于已读。

### R30 — 可观测性、诊断关联与成本
- 跨语言诊断关联、bounded telemetry和credentials/参数脱敏，诊断队列不能破坏预算。
- 如何跨FFI关联trace而不复制大量状态；采样/metrics cardinality如何有界；错误诊断如何保留native stack
