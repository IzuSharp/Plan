### Source predictions that require runtime confirmation

For full narrow results with B=32 and no byte split, the existing [BatchResultTests][batch-tests] source expects 1/2/4/32 pull generations for 1/32/100/1000 rows, one close generation and one SQL execution. SQLite normally predicts 2/33/101/1001 step calls, including observed EOF. These are not executed counts in this checkpoint. Early stopping, byte quotas, busy retry, DDL reprepare, transaction controls and setup may change other counts; preserve their own populations.

`SQLITE_PREPARE_PERSISTENT` is not physical statement reuse; the pinned SQLite source uses it to disable statement lookaside allocation. Dapper `[CacheCommand]` is not proof of SQLite statement retention because recycle detaches the connection and finalizes statements in this provider. Observe physical handles/prepare/finalize directly before calling the workload unequal or assigning a cost to that distinction. PG command reuse likewise does not imply explicit prepared statements; the current reference disables MaxAutoPrepare and has no explicit phase Prepare call.
