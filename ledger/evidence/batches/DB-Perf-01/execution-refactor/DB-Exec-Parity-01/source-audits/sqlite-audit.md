## Two corrections to naïve attribution

### Dapper command caching does not establish SQLite statement caching

The current prepared Dapper workload annotates `Reused` with `[CacheCommand]`; dynamic sites have `[CacheCommand(false)]`. Dapper.AOT’s generator emits `TryReuseThreadStatic` / `TryRecycleThreadStatic`. Both thread-static and interlocked recycle helpers set `command.Connection = null` before caching. Microsoft.Data.Sqlite’s `SqliteCommand.Connection` setter calls `DisposePreparedStatements()` whenever the connection object changes; this disposes every statement handle, which reaches `sqlite3_finalize`.

Thus a reused managed command is not proof of a reused physical `sqlite3_stmt`. With these exact generated factories, normal recycle detaches the connection and invalidates the prepared statement. Verify the emitted factory and native counters before assigning a prepare-count difference to Korda. A direct `SqliteCommand` held on the same connection is a useful separate isolation lane, but must not be relabeled Dapper.AOT’s ordinary path.

Korda also calls `sqlite3_prepare_v3` in each `ProviderConnection::prepare` and `sqlite3_finalize` in `ProviderStatement::close`; a prepared Korda query reuses logical plan/layout, not a cross-execution physical SQLite statement. The flag `SQLITE_PREPARE_PERSISTENT` is not a cache: SQLite `prepare.c` uses it to disable lookaside allocation for the statement. The default Microsoft.Data.Sqlite `sqlite3_prepare_v2` path has zero public prepare flags. That flag asymmetry is a measurable allocator hypothesis, not an established bottleneck.

### SQLite async names do not imply comparable thread handoff

Microsoft.Data.Sqlite `ExecuteReaderAsync` checks cancellation and returns `Task.FromResult(ExecuteReader(behavior))`. `ExecuteReader` calls `NextResult`, which prepares, binds and performs the first `sqlite3_step`. Its first `Read()` consumes the already-stepped row; subsequent reads step again. Dapper’s async method may consequently complete substantial work synchronously on its caller thread.

Korda’s `CursorPull::request` constructs request owners and posts work to `Source::workers`; its pull then publishes a ready callback, managed take, fenced continuation, and eventually DTO reads. Comparing time labelled “ExecuteReader” against time labelled “open” would charge different work to each stage. The semantic boundaries must be **before submission → actual driver start → first engine row → first user DTO → EOF/cleanup**, with thread IDs and thread CPU time on each side. No scheduler cost has been measured here.

### Exact-full batch case has an existing correctness oracle

`tests/Data.NativeHost/BatchResultTests.cs` already checks 0/1/32/64/100/1000 rows with B=32, requiring `count / 32 + 1` request/ready/take/publication events, one final close, and one SQL execution. For a 1000-row result that predicts 32 pulls; a 32-row result predicts 2. This is source and existing test intent, not a new executed test receipt.

`native/cpp/tests/streaming_tests.cpp` separately preserves complete dynamic shape before scalar failure, byte-full lookahead error precedence, queued cancellation with no provider step, and separate metadata/first-fetch effects. `native/cpp/tests/fixtures/sqlite.cpp` preserves early close with no draining of remaining engine rows and cancellation that cannot interrupt the next generation. Managed `AllocationProbeRaces.cs`, `BorrowedBatchFixture.cs`, `RowLeaseReuseChecks.cs` and native pull race tests cover mapper/Dispose and borrow retirement. Physical statement reuse must also prove DDL invalidation, reset result/error handling and clear-bindings semantics; SQLite’s automatic reprepare in `sqlite3_step` alone does not prove those contracts.

## Minimal diagnostic work after the locked builds are available

1. Freeze four ordinary Release Native AOT consumers first. Store command arrays, environment/CPU affinity, dependency locks/assets, generated `.cs`, executable/native-library/debug-file SHA-256 and ELF build IDs. Hash the original and diagnostic candidates separately. Use matching symbols with `objdump -d -C -S`, DWARF line tables and `addr2line`; an unbound sample address or source-only symbol is not a measured hotspot.
2. For SQLite, record actual `sqlite3_sourceid`, version, complete sorted compile options, opened database PRAGMAs, actual mapped image and engine compile command. Same engine source with different flags is not sufficient parity.
3. Use an independent local diagnostic build with per-thread fixed buffers (no per-event strings/console output). Event fields: query ID, batch/generation, phase, `CLOCK_MONOTONIC` ns, Linux TID, `CLOCK_THREAD_CPUTIME_ID` ns, operation/column count, bytes. Time both sides of each asynchronous boundary; do not subtract CPU clocks from different threads. Record event-drop counters and measurement overhead.
4. Instrument both SQLite paths at prepare/bind/step/column/reset/finalize boundaries. Korda statically links SQLite with hidden exports; ordinary LD_PRELOAD interposition of `sqlite3_*` cannot be assumed to see its internal calls. Use a separately built diagnostic provider or engine wrapper with explicitly verified coverage. Count `sqlite3_stmt_status` RUN/VM_STEP/REPREPARE/FULLSCAN_STEP/SORT and MEMUSED at meaningful boundaries, plus `sqlite3_trace_v2` statement/profile events if needed. Different notions of a trace statement, engine VM run, API step, and business request stay distinct.
5. Emit stage/byte totals for the public single-PK, 100/1000 narrow, 32 exact-full and early-stop cases. Then split the 35-case mixed contract by business kind. Reuse historical Go long runs; its physical prepared reads and handwritten DTO mapping are a contrast, not proof that Korda’s native boundary is cheap or expensive. Measure one matched Go query only for an unresolved cause.
6. First prove whether per-row engine-adjacent/managed materialization work or per-batch scheduling accounts for the thousand-row amplification. Then isolate prepare flags/statement caching, codec/descriptor scans, native buffer copying and callback/close costs. The ordering here is an **observation priority**, not an optimization decision based on measured benefit.
