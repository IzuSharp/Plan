## 模块与接口

Implement the exact D20 domain-neutral work-item reference service with operations, items, outbox and attachments. Do not replace it with an additional durable job/attempt/claim/complete state machine or import ArcForges business behavior.

C# 接口：

Static Item, OperationResult, OutboxEvent and Attachment DTO/entity declarations; POST /v1/items, keyset GET /v1/items, GET /v1/operations/{id}, and authorized attachment PUT/GET. Natural typed Fluent and C# business Handlers consume mandatory Rust DB/ORM/Server; optional protocols call the same service.

Rust 原生复用：

SQLx/SeaQuery and selected Rust host; use native transaction/relations/streaming implementation from B04/B14/B17.

## 实施步骤

1. Implement D20's four-table schema and explicit migrations for both PostgreSQL and SQLite. Preserve operations(scope,request_key) uniqueness, stable operation_id, tenant/item keys, expected version and outbox event identity. Freeze v1 request-hash length-prefixed UTF-8/integer golden vectors and response-version bytes; do not infer a universal JSON canonicalizer.
2. Create items with authenticated scope, validated 1-128 ASCII idempotency key and request hash. The unique operation record, business write, stable replay response and outbox row commit in one Rust-owned transaction. Same key/hash replays; different hash returns 409 without changing the winning record.
3. For PostgreSQL ReadCommitted, ON CONFLICT DO NOTHING returning no row is followed by a separate SELECT statement and hash/scope verification. For SQLite use short BEGIN IMMEDIATE writer admission. COMMIT Unknown returns the D20 outcome_unknown recovery identity/503 when HTTP remains available; missing recovery data does not prove rollback or permit unprotected replay.
4. Implement tenant-authorized keyset listing with (created_at,id), maximum 100 rows and tamper-resistant scoped cursor, plus authorized operation-result recovery. No cross-page snapshot guarantee is invented; any consistent export uses its explicit bounded transaction/stream profile.
5. Implement the outbox worker with bounded claim/lease batches, external publication after its claim transaction ends, stable event_id, explicit retry/backoff and acknowledgement recording. Include an independent persistent deduplicating consumer; at-least-once delivery can repeat attempts and does not promise external exactly-once effects.
6. Implement attachment PUT/GET with authorization, 64MiB route length, 32KiB chunks and finite disk/byte/upload budgets. Stage, hash and durably finish the blob before same-filesystem immutable rename, then commit the authorized DB reference/result/outbox. Retain staging/recovery manifests and a grace period so orphan collection cannot delete an active upload or recovery blob; never hold a DB transaction during the client upload.
7. Apply D20's 7-day idempotency retention profile and protect records referenced by recovery/outbox. Do not promise replay after expiry or remove tenant/principal/operation scope. The initial operations table stores confirmed replayable results, not a separately committed InProgress job state.
8. Use explicit finite CloseAsync on HTTP completion: Pending keeps native parents, roots, callbacks and budgets in the Engine, without retaining an ended request context/DI scope. Do not follow Pending with an implicit indefinite await-using join; already-dispatched COMMIT uses its independent deadline and outcome semantics.
9. Supply clean independent NuGet consumers for both real databases over the Rust HTTP1/2/TLS Host on Windows/Linux AOT. Normal model/DTO/Handler edits retain the native module hash, require no Cargo and obey D18's separate managed/native and per-request payload credits.

## 错误、取消、内存与并发

- ACK loss never blindly repeats a non-idempotent mutation. HTTP response loss after a known commit leaves the durable same-key replay record intact; Unknown stays distinct from known rollback and confirmed success.
- Outbox publish success followed by acknowledgement-write failure may cause another delivery attempt; the independent consumer proves one business effect under stable event_id deduplication.
- Blob and database are not a distributed atomic transaction. A failed reference commit may leave an unreferenced blob, but a successful DB reference must never name an incomplete blob; authorization always comes through the tenant's DB reference.
- Cancellation, Body EOF and handler return do not free retained DB/response owners. Finite HTTP cleanup can stop waiting while the Engine still accounts for every pending owner and cancellation registration.

## 验收要求

- Run the complete D20 REST API through real HTTP -> C# Handler -> Rust query/database on both Windows/Linux AOT and PostgreSQL/SQLite; verify static hash/response golden vectors, no-Rust ordinary build/run and unchanged native bytes after entity/Handler edits.
- Concurrent same-key same-hash requests produce one item/operation/outbox effect and the same replay response; different hash and cross-tenant/principal scope attempts cannot expose or overwrite another result. Exercise PG conflict snapshot and protected Unknown recovery.
- Execute an outbox duplicate-attempt oracle and attachment upload/download/orphan-grace oracle. Demonstrate blob durability before DB reference, bounded streaming without a held upload DB session, and authorization even for an existing shared content hash.
- Verify the declared retention window, keyset tie-breaker/cursor scope and 1MiB JSON/100-row/64MiB attachment limits. CloseAsync Pending may end HTTP waiting but live owner counters and budgets remain until actual safe retirement; B22 supplies the full fault/soak matrix.
