## 可执行实现设计：字节预算、保留帧和通道关闭

本任务消费选中的 host profile；B15/B17 的 selection_inputs 必须决定且至少一个 selected，selected host 的精确实现作为条件 start 依赖。两者都 selected 时分别通过同一公开流语义，不引入全局默认。C-SERVER-001@0.2.1-draft/C-BUFFER-001@0.1.0-draft 接受和未来实施授权仍是前置。

按连接数、在途请求数、admitted handler、input/output retained bytes、等待写入、body lease 分开记账。请求 head 发布只结束 head Future 的许可；body EOS/Drop、所有 retained frame 和 callback retirement 才能结束各自预算。Tokio channel 条目容量、Tower Service concurrency 和 HTTP/2 window 都不能单独给出整个请求或 RSS 的上界。

| 候选接缝 | 所有权/预算约束 | 失败与关闭 |
| --- | --- | --- |
| RequestBudget / BodyLease | 在准入时保留 request/byte 额度，取消不直接销毁仍有引用的 owner | 拒绝超限须在不可控分配/接管之前；已接管资源必须有回收者 |
| ReadBodyAsync | 返回有 owner 的只读分片或受限 copy；记录保留的 allocation | 小 slice/clone 可保留大块 Bytes；按真实保留 backing allocation 的保守上界计账 |
| WriteBodyAsync | byte budget 与 queue slot 均在接管前取得；发送/丢弃显式转移责任 | 超大 chunk 切分或拒绝；queue 满/取消归还所有已取额度 |
| Retained frame owner | 仍共享 owner 的 clone/非空 slice 共用账本；空 slice 与深拷贝按真实 owner 分开计账，最后共享引用退出才归还 | 不因 len 变小、HTTP/2 credit 归还或 head Task 结束而提前退账 |
| Channel reservation | reserve permit 与业务 admission 独立，记录谁持有 outstanding permit | receiver.close 后旧 permit 仍可能发送，不能假设 close 立即意味着队列排空 |

先在统一准入协议内决定工作是否被接管，再把 reservation、bytes 与 owner 交给单一责任方。关闭线性化点前已接受的工作按 D18 drain；之后的新工作拒绝，即使底层 permit 仍有效也不能偷渡为新业务。queue receiver 的 close、最后 outstanding permit 消失、所有消息消费/丢弃、body 退出分别记录。pending sender 不能通过无限 Tasks/缓冲/等待者绕过预算。

验收必须固定可控顺序：取 permit→close receiver→旧 permit send/drop；head 已完成但慢 body 活跃；小 slice 留住大 backing allocation；巨大 chunk；慢读者；半关闭；write 错误；取消/Close 并发；consumer 提前退出；TLS 失败。观测账本峰值与归零、真正 retained bytes 和整体 RSS，分别报告未计入的 socket/TLS/allocator/线程内存。资源计数正确不是 whole-RSS 已有硬上界的证明。

正式测试运行两个 OS 的真实 AOT handler 与各 selected host；流字节序列/EOS/error 不能丢、重或乱序。Design run 43375871731 的 Windows/Linux 各六项 retained-Bytes/Tokio 探针只证明其执行的底层反例，不能代替跨语言 owner 传递、网络负载或长期 p99/RSS 验收。

预算里的 A 必须包含 Closing/retirement-pending 请求：已停止业务但仍持有 frame/permit/context 的请求不可从 active 账本扣除后无限再准入。Body::poll_frame 返回 None 只记录 EndObserved；若公开 Hyper 接缝无法区分某个 NO_ERROR reset，不伪造 NormalTransportCompletion。精确传输完成原因要独立能力协商与真实证据，不默认 fork。
